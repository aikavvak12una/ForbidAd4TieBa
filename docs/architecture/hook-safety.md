# AI Code Direction Guide

本文件用于指导 AI 修改或审查本工作区内的 Xposed、LSPosed、反编译宿主适配类项目。目标是让符号解析在宿主更新时可靠地失败而非静默出错、降低运行时 hook 开销、减少冗余 fallback，并让变更可审查、可验证、可维护。

本指南是工作区级通用规则，适用于所有模块。开始任务时必须先识别当前项目、目标宿主、符号解析架构和验证方式，再套用下面的约束；不要把某个项目的目录名、包名、解析器名称或 UI 文案位置当成全工作区通用事实。

## 核心原则

以下原则贯穿全文，后续章节只在具体场景中引用，不再重复展开。

- **复用优先**：遇到通用问题或成熟领域能力时，先检索并评估 GitHub 上的成熟开源实现、库或实践；有可靠方案时优先参考或复用，而非自行实现。复用前确认许可证、维护状态、体积影响、运行时成本和适配边界是否与当前项目约束兼容。
- **第一性原理调试**：先还原系统真实输入、状态、调用链和不变量，再建立可证伪假设，不按表象或历史经验盲目修补。优先构建可重复的反馈环，确认根因后再做最小修复和回归验证。
- **Fail closed**：符号解析失败、候选不唯一、置信度不足、资源或结构特征不稳定、依赖条件不满足时，一律禁用对应功能并输出一条可定位原因，不追加猜测式 fallback，不影响其他功能。
- **单版本基线**：适配与验收只以宿主当前最新版为基线。功能失效后按当时的最新版重新修复，不为历史版本保留兼容分支、版本条件判断或降级路径。
- **结构化解析**：放弃多版本覆盖不放松解析要求，反而抬高。多版本适配原本靠"同一条规则在两个样本上都成立"来筛掉过拟合；只剩一个样本后这道交叉验证消失，必须由规则自身的判别力补上——每条规则要靠结构特征唯一确定目标，且至少包含一个语义锚点（字符串常量、资源名、对 Android SDK 或宿主稳定 API 的调用、协议字段名）。纯形状特征（返回值、参数个数、字段数量、方法名长度）判别力随宿主演进快速衰减，不得作为唯一判据。
- **最小变更**：只做与当前任务直接相关的改动（详见第 2 节）。

## 0. 工作区上下文

常见目录含义：

- 模块源码：例如 `tbhook_api101`、`BBZQ`、`qb-rewardskip-api101`、`bili-adskip-api101` 等。
- 宿主反编译代码：例如 `tieba`、`bili`、`qb` 等，用于验证宿主行为、调用链、资源和 hook 点。
- 宿主逆向工具：除已有反编译目录外，可能还有 jadx CLI（宿主机）和设备侧的 MT管理器 MCP（工具名 `mcp__mt-apk__*`，需先建 adb 端口转发）。结构性问题（锚点是否存活、谁引用了它、父类是什么）优先用 MCP，通读整段逻辑用 jadx。具体连接方式与可用性由各模块文档说明，不要假定所有模块都已接通。
- Xposed/LSPosed API 参考：例如 `libxposed102`、`xposed api101` 或同类文档目录。
- 本地 Android 设备：不要假定固定端口。用 `adb devices` 确认在线设备，再按需决定安装、重启或抓日志。

任务开始前必须明确：当前要修改的模块源码目录、对应宿主反编译目录、该模块的符号解析入口与数据模型/缓存/状态输出方式、UI 文案集中位置，以及功能运行在哪些进程、用户关闭后是否应完全短路。

## 1. 工作前确认

修改代码前完成最小必要确认：

- 明确任务目标、成功标准和影响范围；需求不清楚时先提问。
- 阅读相关现有代码，只计划修改完成任务所必需的文件。
- 判断任务是否涉及 hook 点、混淆符号、目标应用资源 ID、UI 文案、运行日志、持久化、后台任务或缓存。
- 说明可能影响的 hook 功能；一个功能的修改不得默认影响其他功能。
- 以对应宿主反编译代码验证目标应用行为；涉及 Xposed/LSPosed API 时，以当前项目实际依赖的 API 文档或源码为依据。

## 2. 修改范围

- 只做与当前任务直接相关的最小变更；不做无关重构、格式化、命名调整、import 清理或代码风格改造。
- 不添加未被需求证明必要的新功能、配置项、兼容路径或扩展性设计；不为了“更优雅”改变已有稳定逻辑。
- 公共工具只在确实存在多个调用方时抽取；单次使用逻辑不要抽象成框架。
- 已有未提交变更时，不得回退用户或其他工具的改动；先确认哪些文件与当前任务相关，再在原有变更上继续。

## 3. 混淆符号与符号解析架构

目标应用中混淆的类、方法、字段必须统一通过当前模块的符号解析架构解析。常见形态：

- 单文件解析器：例如 `HookSymbolResolver.kt`。
- 分层解析器：例如 `BiliSymbolResolver.kt` 负责扫描，`BiliHookSymbols.kt` 负责符号数据、恢复、缓存版本和状态模型。
- DexKit 或静态扫描辅助：例如 `DexKitBridgeProvider`、`DexKitRuleVersions`、`MethodDescriptor`、`FieldDescriptor`、`HookPointStatus` 等。

新增或修改混淆 hook 点前，先找到当前模块的符号解析入口和符号数据模型。业务 hook 只消费已解析、已恢复、已校验的符号或安装计划。

### 3.1 硬编码禁止事项

本节约束同时适用于业务 hook 和符号解析器内部的规则常量。混淆符号写在扫描器里不会因为"它在解析层"而变得安全——它同样是对单个 APK 样本的写死。

- 不得硬编码混淆类名、方法名、字段名、R8 样本名、匿名类名或短包名；不得把反编译样本中的 `a`、`b`、`h`、`FJ0.c`、`BL:`、`r8-map-id` 等符号直接写入业务逻辑。
- 不得在业务 hook 中自行扫描类、遍历方法、猜测字段、搜索 Dex、解析反编译字符串或追加业务层 fallback。
- 扫描规则中不得把混淆符号用作匹配条件、候选过滤条件或评分加分项。以混淆名加分（例如"方法名等于 `w1` 则 +30"）不构成硬性依赖，但会在宿主更新后把分数偏向错误候选，属同类禁止项。
- 不得用方法名、字段名或类名长度作为候选资格、加分项或排序判据；也不得按字母序、反射枚举顺序或猜测匿名类后缀选取目标。名字排序仅可用于诊断展示或已全部选定目标的序列化，不得影响入选结果。

允许直接硬编码的范围仅限：

- Android SDK、Java/Kotlin 标准库、Xposed/LSPosed API。
- 宿主中明确未混淆且跨版本稳定的公开类、公开方法或协议字段。
- 当前模块自身的类、资源和配置 key。

即使允许硬编码稳定宿主类名，若该类参与 hook 安装计划，也应优先在符号解析器中统一验证和缓存。

### 3.2 符号解析器职责

- **候选发现**：通过 DexKit、类名关键字、接口实现者、继承关系、方法签名、字段结构、调用链、关键字符串、资源上下文等发现候选。
- 本项目的 Dex 候选枚举和字节码证据只由 DexKit 提供，反射负责结构验证及描述符恢复；不保留 `DexFile` 等另一套枚举路径。扫描所得的动态名称可以写入缓存并用于恢复，但不能反向抄成生产规则。具体边界见 [Symbol discovery](symbol-discovery.md)。
- **结构验证**：用参数类型、返回值、字段数量与类型、接口/父类、构造函数、调用关系、关键字符串组合等多维特征交叉验证。
- **唯一化**：候选必须唯一或能被稳定规则明确分流，否则 fail closed。
- **评分制的唯一化**：绝对阈值不构成唯一化。评分制总能产出唯一的最高分，因此"取最高分"永远满足"候选唯一"，这条不变量在评分路径上是失效的。采用评分排序时必须同时要求最高分与次高分的差距达到下限；差距不足（尤其是同分）按候选不唯一处理，fail closed 并记录候选列表与各自得分。禁止用字母序、类名、方法名长度等与目标语义无关的字段做平局裁决——同分意味着两个候选携带的证据完全相同，此时任何裁决都等价于随机选取 hook 目标。
- **两种失效必须区别对待**：无候选通过阈值会产生 `MISSING`，有信号、可被发现、可被修复；同分裁决会产生"唯一但错误"的匹配，无信号、不会触发修复，是持续维护模式下唯一无法自愈的失效。规则设计应优先保证后者不发生。
- **符号表生成**：输出轻量的 class/method/field/resource 描述符或安装计划。
- **恢复与校验**：后续启动时从缓存恢复 `Class`、`Method`、`Field`，并确认签名仍匹配。
- **缓存**：基于宿主指纹、模块版本、补丁状态、符号规则版本等稳定条件判断缓存有效性；条件未变时不重复全量扫描。
- **状态输出**：为每个 hook 点输出可定位状态，例如 `HookPoint[...] state=FOUND/MISSING/ERROR/OPTIONAL` 或当前模块等价状态。
- **错误隔离**：单个 hook 点扫描异常不得中断其他 hook 点扫描。不得用 `getOrNull()`、空 `catch` 或静默 `null` 吞掉异常；可恢复的子扫描异常须记录到扫描日志或 `scanErrors`，并 fail closed 禁用对应功能。

反编译代码只能作为寻找稳定特征的依据。单版本基线下允许规则只在最新版验证通过，但不允许把样本里的偶然特征当作判据——区分"这个类之所以是目标"（语义锚点、调用关系、协议字段）和"这个类在本次构建里恰好长这样"（字段个数、参数排列、混淆名），是失去多版本交叉验证后唯一还在起作用的防过拟合手段。

### 3.3 新增或修改混淆 hook 点时必须同步

按当前模块架构补齐：

- 符号数据类或安装计划字段。
- JSON/SharedPreferences/文件缓存的序列化与反序列化。
- restore/recover 方法及签名校验。
- cache schema、rule version 或等价缓存失效版本。
- `HookPoint[...]` 状态输出、子 hook 点状态、feature status map 或等价状态。
- 扫描异常捕获与 `scanErrors`、日志、状态报告。
- 用户配置项与功能可用状态的一致性判断。
- 关闭功能时的扫描、hook 安装、回调、后台任务和持久化短路。

## 4. 资源 ID 与资源访问

目标应用资源 ID 会随版本、渠道包、资源重排或补丁状态变化。单版本基线不放松这条约束，反而使它更关键：同一版本内不同渠道包和补丁状态的资源 ID 就可能不同，且硬编码的数值在宿主更新后不会抛异常，只会静默指向另一个资源——属于"唯一但错误"类失效，不会被持续维护流程发现。

- 业务代码不得写入目标应用的数字资源 ID（`0x7f...`、十进制 ID，或从日志/反编译抄出的目标 `R.id`、`R.layout`、`R.string` 数值）。
- 需要访问目标资源时，在安装或扫描阶段通过资源名、包名、类型和可验证上下文解析，并预计算为轻量状态；资源名、布局结构、View 层级或文案特征不稳定时 fail closed。若资源 ID 属于混淆 hook 点安装计划的一部分，应与符号解析器的扫描结果、缓存、状态输出保持一致。
- 允许硬编码的资源 ID 仅限 Android SDK 或本模块自身资源；引用本模块资源必须用生成的 `R.xxx.xxx` 常量，不写死整数值。
- UI 查找 View 时优先使用稳定结构、明确父容器和类型校验；找不到、类型不符或候选不唯一时短路径退出并保留可定位日志。

## 5. Hook 性能

运行期 hook 回调必须轻量：

- 回调中不得执行类扫描、方法遍历、复杂反射、资源查找、DexKit 查询、文件 IO、数据库操作、网络请求或大量日志。
- 能在扫描阶段、首次主进程启动或 hook 安装阶段完成的解析、校验、预计算，一律不放到回调中。
- 回调依赖的状态预计算为布尔值、集合、函数引用、描述符恢复结果或轻量数据结构；回调本身只做简单判断、读取参数、修改返回值或短路径退出。
- 调试型大对象日志默认关闭，或受显式开关、采样和长度限制保护。

## 6. 模块轻量化

模块应小而专注，避免为单个 hook 功能引入长期维护和体积成本。

- 不引入未被需求证明必要的新依赖、SDK、框架、动态脚本引擎或大体积工具库；能用 Android/Xposed/Kotlin 标准能力完成的不新增第三方依赖。
- 不把目标应用反编译代码、资源、APK、临时扫描产物、完整日志或调试 dump 打包进模块。
- 新增依赖、资源或 native 文件前必须说明用途、体积影响、运行期成本和替代方案；无法证明必要时不添加。
- 调试工具、详细日志、导出能力和实验性代码默认关闭；仅在显式开关、debug 构建或明确诊断路径下启用，并设置长度、频率和生命周期限制。
- 删除功能或迁移实现时，同步清理不再使用的依赖、资源、配置项和缓存字段，不保留”可能以后会用”的负担。

### 6.1 文件规模与职责边界

单文件膨胀的成因不是”代码写多了”，而是**存在一个没有天然边界的容器**：一个顶层 `object` 或 `class` 里，每新增一个 hook 点就往同一命名空间追加常量和函数，没有任何机制迫使它分裂。相比之下，按功能域一个文件的扫描器目录能长期维持单文件规模，因为约定本身提供了边界。因此规则针对容器，而非行数。

- 新增 hook 点时，其候选发现与结构验证规则必须落在**按功能域划分的独立文件**中，不得追加到符号解析入口或任何已有的聚合 `object` 里。
- 符号解析入口只保留编排职责：扫描调度、缓存读写与失效判断、指纹计算、状态汇总、对外查询 API。具体 hook 点的规则细节、平台无关的工具函数、UI 提示不属于入口。
- 单个功能 hook 文件只承载该功能的 hook 安装与回调。其符号规则归符号解析器，用户可见文案归文案入口，配置读写归配置管理，统计与持久化归对应模块。一个功能 hook 文件超过千行，通常意味着这四类职责混在了一起。
- 常量是拆分受阻的主要原因：迁移逻辑时常量被留在原处，导致新文件反向依赖旧容器。常量应随其**唯一消费方**一起迁移，只有确实存在多个消费方的才留在共享入口。
- 单文件超过 800 行视为需要拆分的信号，超过 1500 行应在本次或下一次触及该文件的任务中拆分。按职责边界切分，不按行数机械切分；无法说清切分边界时，说明职责本身还没理清，此时不要切。
- 拆分属于结构调整，不得与功能修改混在同一次变更中提交，否则无法审查也无法回滚。

## 7. 功能解耦、生命周期与 fallback

- 每个功能有独立 hook 安装入口；一个功能失败不得影响其他功能。
- 模块启动路径懒加载、按功能开关安装 hook；未启用的功能不得初始化扫描器、后台任务、缓存读写或大对象状态。
- 每个用户可配置项都有明确生效边界：开启时只安装该配置需要的逻辑；关闭时对应的 hook 安装、扫描触发、后台任务、缓存读写、监听器和回调路径全部卸载或短路。
- 配置项依赖的扫描结果必须和功能状态一致；扫描判定不可用时即使用户开启配置也应 fail closed 并给出可定位原因。
- 非目标进程、非目标包名或功能未启用时尽早退出；不得在所有进程中初始化全局单例、线程池、定时器或广播监听。
- 多个功能 hook 同一方法时，检查执行顺序、参数修改和状态冲突；不引入隐式全局状态依赖，不混杂 UI 配置、符号解析和 hook 回调逻辑。
- 不添加重复 hook、重复符号解析、多套实现路径或“保险起见”的反射兜底。发现已有 fallback 时先判断是否必要：能迁移到符号解析器的不留在业务 hook，能安全删除的删除。

## 8. UI 文案

用户界面可见文本必须放在当前项目既有的集中位置（如 Android 资源 `src/main/res/values/strings.xml`、Kotlin 文案对象 `UiText.kt`，或项目已有的 Compose/资源封装入口）。开始前先确认当前项目模式，不要把某个项目的文案位置套用到另一个项目。

- Activity、View、Dialog、Adapter、Compose UI 和 hook 逻辑中不得散落用户可见文案；日志、调试信息、内部错误描述可不放入。
- 新增文案前先检查是否已有可复用内容；修改文案时不顺手调整无关文案。

## 9. 运行日志与持久化

根据运行日志优化时，优先处理会持续消耗性能或淹没日志的问题。

- 遇到 `EACCES`、`Permission denied`、文件不存在、目录不可写等持久化失败时，不得只吞异常后继续高频写入；应记录一次清晰原因，并进入退避、禁用本轮持久化或切换到内存态。后台任务失败同样须有退避、失败计数或停止条件，避免持续重试和刷屏。
- 统计、缓存、调试导出类文件优先使用应用自身可写目录，写入前确认父目录存在。
- 高频信息流、列表、图片、消息等 hook 中不得默认输出完整对象、完整 JSON、图片 URL 列表或大字段；结构排查输出摘要即可，完整 dump 必须由显式调试开关控制并设总长度上限。
- 优化后如条件允许，复查 `runtime.log`、模块日志或 logcat，确认同类警告没有持续重复。

## 10. 验证要求

完成修改后尽量执行相关构建、测试或静态检查，重点确认：

- 项目能否编译，相关 hook 功能是否仍然独立。
- 混淆 hook 点是否全部通过当前模块符号解析器；是否没有硬编码目标应用资源 ID，资源解析失败能否 fail closed 且不影响其他功能。
- 新增或修改的混淆 hook 点是否出现在符号扫描状态中，成功为 `FOUND` 或等价状态，失败能看到 `MISSING`、`ERROR` 或具体缺失字段/异常原因；扫描异常是否被捕获并进入扫描日志、`Scan Errors` 或对应状态，且不导致其他 hook 点状态缺失。
- 扫描结果是否准确反映功能可用性，用户配置项是否只在依赖条件满足时生效。
- **宿主更新回归**：单版本基线下，宿主版本变化是符号失效的唯一触发点，也是唯一需要回归的时机。宿主更新后必须导出一次全量 hook 点状态，与更新前的快照做 diff，确认 `FOUND` 数量和具体 hook 点没有非预期变化，再判定适配完成；仅"编译通过 + 装上没崩"不构成完成。diff 出的 `MISSING` 逐个按最新版修复；diff 未变但功能实际异常的，优先怀疑"唯一但错误"的匹配，检查该 hook 点的候选得分差距。
- 反混淆扫描是否只在缓存缺失、失效或目标指纹变化时执行；后续启动和 hook 回调是否只走轻量路径；用户关闭的功能是否完全卸载或短路且不再产生持续性能消耗。
- 模块是否没有新增不必要依赖、资源、后台任务、打包产物或默认开启的调试能力；UI 文案是否仍集中在既有入口；是否没有引入重复 fallback、冗余实现或持续刷屏日志。

无法运行完整构建或日志复查时，必须说明原因，并至少完成静态检查。

## 11. 输出要求

完成修改后按任务规模输出。涉及 hook、混淆符号、资源、运行期行为或配置项时，优先包含：

```text
1. 修改了哪些文件及修改目的
2. 面向哪个模块源码和哪个宿主反编译目录
3. 检测目标功能和可能受影响功能是否正常运行的步骤
4. 是否涉及符号解析器，入口和数据模型是什么
5. 是否涉及混淆 hook 点
6. 是否涉及目标应用资源 ID，是否存在硬编码
7. 是否涉及 UI 文案，放在哪个集中入口
8. 是否新增依赖、资源、后台任务或其他体积/启动成本
9. 是否新增、移除或保留 fallback
10. 已执行的验证命令和结果
11. 未能验证的内容和原因
12. 如涉及运行期问题，是否复查日志及剩余风险
13. 如新增或修改混淆 hook 点，说明状态输出、异常捕获路径、日志复查结果，以及该规则依赖的语义锚点和唯一化方式（评分制须说明分差下限）
14. 下一步建议，优先说明最值得继续验证、观察或清理的事项
```

如果任务只修改文档、注释或纯配置，可简化为变更摘要、验证命令和未验证内容。

## 12. 推荐流程

```text
1. 阅读需求和相关代码
2. 识别当前模块源码、宿主反编译目录、符号解析器、UI 文案入口和验证命令
3. 判断是否涉及混淆 hook 点、目标应用资源 ID、Xposed/LSPosed API、UI 文案、运行日志或持久化
4. 混淆符号统一放入符号解析器解析和缓存，每条规则确认语义锚点与唯一化方式（评分制须有分差下限）
5. 目标应用资源 ID 禁止硬编码，统一在安装或扫描阶段解析并预计算
6. 确认扫描结果、功能状态和用户配置项一致；关闭的功能不安装 hook、不执行回调、不保留后台消耗
7. 以最小范围修改代码，避免增加不必要依赖、资源和启动成本
8. 验证编译、hook 独立性、回调性能、模块轻量化和日志表现
9. 输出简洁修改报告，并给出下一步建议
```
